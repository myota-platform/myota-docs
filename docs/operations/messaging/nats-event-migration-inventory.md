# NATS migration Phase 0 inventory and selected topology

**Status:** current-state inventory plus an accepted target-design decision
recorded at the workspace owner's request. Runtime implementation and
deployment qualification remain open.

**Scope:** event writes, asynchronous work, relay and consumer paths found in the
authoritative repositories on 9 October 2026. Paths name the owning repository
first. Deploy and platform copies are mirrors. This is a source audit, not a
production broker inspection or a runtime test.

**Time qualifier:** Event rows and profiles below preserve the 9 October
baseline. Phase 2 relay source behavior and the 10 October read-only live-broker
inspection are recorded separately below; do not interpret a source change as
proof that production has deployed it.

### Phase 2 source and live-state update — 10 October 2026

- **Current source behavior:** `myota-deploy/services/outbox_routing.py` now
  routes registered facts to `myota.events.<eventType>` with dotted tokens,
  validates producer ownership and UUID/time fields, and keeps the six mapped
  Geodata source event types on their registered legacy work subjects. The relay
  enforces the configured serialized-message cap and marks an outbox row only
  after JetStream acknowledgement.
- **Topology ownership:** `myota-deploy/services/outbox_worker.py` now validates
  the existing stream and durable settings read-only. It does not create or
  update streams/durables. The Geodata worker no longer deletes the retired push
  durable during startup; cleanup waits for a reviewed drain and disposition.
- **Live broker evidence:** A read-only query on 10 October observed the
  file-backed `MYOTA_EVENTS` stream with Interest retention, subjects
  `myota.events.>` and `myota.geodata.>`, one replica, and zero stored messages.
  It also confirmed the broad Activity pull durable and the four Geodata work
  durables with explicit ACK and their current filters. No live broker object was
  changed by this inspection.
- **Boundaries:** The isolated Phase 2 test used disposable NATS and PostgreSQL
  in `myota-phase2-test`; its namespace was removed after validation. The current
  production stream, existing broad Activity durable, legacy Geodata work
  subjects, and deployed consumer delivery handlers remain unchanged. The
  Activity durable's narrower successor filter requires the Phase 3 transition
  because the current Interest-retained durable cannot be edited in place safely.

## Evidence model and shared behavior

The profiles below avoid repeating the same transport facts on every event
row. Each event row points to a producer profile and routing class; the profile
supplies the transaction, envelope, processing, retry, source of truth, replay,
deployment, and known evidence gaps for that row.

### Identity domain facts — profile I

- **Owner and database:** Identity; `myota_core`.
- **Write path:** `IdentityHandler` writes versioned events through `Store.event`
  and flushes state plus outbox rows in `Store.persist`, both in
  `myota-identity-service/common.py`. Event IDs are generated by the helper;
  the `Store.persist` database transaction is the outbox boundary.
- **Current routing:** `myota.events.` plus the event type with periods replaced
  by underscores. The shared Activity durable matches this subject.
- **Consumer behavior:** The Activity handler creates notices for all
  `identity.*` types and deduplicates by event ID. Notification insertion and
  `consumer_processed_event` checkpointing use separate repository transactions,
  so the side effect and checkpoint are not atomic. Identity has no owned
  JetStream consumer.
- **Authority and envelope:** Identity database state and `securityEvents` are
  authoritative. The shared relay envelope is described in profile R below.

### Programme domain facts — profile P

- **Owner and database:** Programme; `myota_core`.
- **Write path:** The event helper and persistence are in
  `myota-programme-service/common.py`; call sites are in
  `myota-programme-service/programmes.py`. State and outbox persist together.
- **Current routing and consumer:** Uses the generic subject transformation.
  No Programme consumer was found; Activity's broad durable matches and
  acknowledges these subjects as no-ops.
- **Authority:** Programme database state and outbox.

### Activity domain facts — profile A

- **Owner and database:** Activity; `myota_activity`.
- **Write path:** Direct relational event inserts use
  `ActivityRepository._event` in `myota-activity-service/activity_repository.py`;
  event-producing endpoints and award code are in `activity.py` and `awards.py`.
  Domain mutation and outbox insertion use the same repository transaction.
- **Current routing and consumer:** Generic subjects match the broad Activity
  notification durable, which ignores Activity and award event types and
  acknowledges them. No independent Activity domain-event consumer was found.
- **Authority:** Activity database state and outbox.

### Geodata domain facts — profile G

- **Owner and database:** Geodata; `myota_geo`.
- **Write path:** `Store.event` and `Store.persist` are in
  `myota-geodata-service/common.py`; relational writes are in
  `myota-geodata-service/relational_state.py`; event call sites are in
  `myota-geodata-service/geodata.py`.
- **Transaction boundary:** The relational writer commits its outbox insert
  with the state delta. Some legacy in-memory/fallback paths and multi-step
  upload flows persist in separate transactions; per-row atomicity needs
  verification where noted.
- **Current routing and consumer:** Generic subjects match Activity's broad
  durable. Its handler processes only Geodata `entity.reviewed` and
  `entity.status-changed` events.
- **Authority:** Geodata relational state, import/job records, and PostGIS.

### Explicit Geodata work commands — profile W

- **Owner and database:** Geodata; `myota_geo`.
- **Current routing:** `payload.natsSubject` is allowlisted by
  `myota-deploy/services/outbox_routing.py`; one competing pull durable per
  subject is provisioned by `myota-deploy/services/outbox_worker.py`:
  - `myota.geodata.entity.delete.v1` / `geodata-entity-deletion-v1`
  - `myota.geodata.entity.location-enrichment.v1` /
    `geodata-location-enrichment-v1`
  - `myota.geodata.import.preprocess.v1` / `geodata-preprocessing-v1`
  - `myota.geodata.import.process.v1` / `geodata-import-processing-v2`
- **Delivery:** Explicit ack, 120-second ack wait, maximum 100 deliveries, and
  one pending message per durable by default. The handler heartbeats long work
  and records `consumer_processed_event` checkpoints before ack.
- **Authority and failures:** Work result and lease/state records are
  authoritative. At max deliveries, the consumer writes `dead_letter_event`,
  marks eligible import/processing rows `FAILED`, then terminates. Earlier
  failures NAK with delay `min(5 × delivery number, 60 seconds)`.

### Relay and envelope — profile R

- **Owner and deployment:** `myota-deploy` owns one shared relay implementation,
  deployed once for each physical database (`core`, `activity`, `geo`). The
  authoritative source is `myota-deploy/services/outbox_worker.py`; routing is
  in `myota-deploy/services/outbox_routing.py`.
- **Publish boundary:** Rows are claimed with `FOR UPDATE SKIP LOCKED`. The relay
  publishes with `Nats-Msg-Id` equal to `eventId` and marks the outbox row
  published only after JetStream ack.
- **Retry and dead letter:** Retries use exponential delay capped at 300 seconds,
  with 12 attempts by default. Exhaustion inserts a database
  `dead_letter_event` and marks the outbox row published with a dead-letter
  marker.
- **Current stream:** File-backed `MYOTA_EVENTS` captures `myota.events.>` and
  `myota.geodata.>` with a 30-day maximum age. The relay creates/validates the
  Activity notification durable and four Geodata durables, then transitions a
  Limits-retention stream to Interest retention.
- **Current envelope:** `eventId`, `eventType`, `occurredAt`, `producer`,
  `aggregate`, `correlationId`, `payload`, and `attempts`. There is no
  `schemaVersion`; the `.v1` event-type suffix is the only visible event
  version. `correlationId` is set to `eventId` rather than propagated from
  request context, and no `causationId` is present.

### Activity notification consumer — profile N

- **Owner and implementation:** Activity owns the deployment behavior through
  `myota-deploy/services/activity_notification_consumer.py` and
  `myota-deploy/services/event_consumer.py`; Activity repository/schema ownership
  belongs to `myota-activity-service`.
- **Durable and delivery:** `activity-notifications-pull-v1` filters
  `myota.events.>`. It uses explicit ack, a 60-second ack wait, maximum 10
  deliveries, and maximum 64 ack-pending messages.
- **Handler behavior:** Identity events create `ACCOUNT_SECURITY_EVENT`
  notifications. Geodata `entity.reviewed` and `entity.status-changed` create
  `GEODATA_PROPOSAL_DECISION` notices. Other matched events are no-ops that are
  still checkpointed and acked.
- **Failures and idempotency:** A supported-major mismatch NAKs after 30 seconds.
  Handler errors write a dead-letter row with `attempts=1` and terminate
  immediately, so the broker does not retry those errors. Notification insertion,
  deduplication, and consumer checkpointing are not atomic because they use
  separate connections.

### Activity database jobs — profile J

- **Owner and database:** Activity; `myota_activity`. Deployment is owned by
  `myota-deploy` (Compose/Helm worker); job code is owned by Activity.
- **Persistence and worker:** Schema and claim/update methods are in
  `myota-activity-service/migrations/001_activity_relational.sql` and
  `myota-activity-service/activity_repository.py`. API/domain transactions insert
  `activity_job`; handlers are in `myota-activity-service/activity_worker.py`.
- **Current processing:** The worker polls every second by default, claims with
  `FOR UPDATE SKIP LOCKED`, increments attempts, and processes the job. It marks
  success or requeues with `2^attempts` seconds (capped at 300) up to the default
  maximum of eight attempts; exhausted jobs become `FAILED`.
- **Authority and idempotency:** The job row and result resource are authoritative.
  Most job inserts have no corresponding outbox event. Supplied idempotency keys
  are unique, but handler side-effect idempotency is handler-specific and not
  uniformly evidenced.

Across profiles I/P/A/G, the outbox event ID is the current stable message ID
and the eventType suffix is the current major version. Producers do not define
a distinct work ID for every command, and no payload/schema compatibility
validator was found. Delayed domain facts do not block the already-committed
producer request; a real downstream projection or notification can lag. For
events with no subscriber today, a lost message has no observed current
consumer impact but can break a future integration. For accepted work, delay
leaves the returned job/resource pending and loss must be recovered from its
service-owned row. Operational reconciliation and cleanup are repair/maintenance
paths and should be observable independently from business work.

### Current retention, replay, and topology findings

- **MYOTA_EVENTS currently mixes facts and work.** The relay initially creates a
  file-backed Limits stream with a 30-day max age, provisions known durables,
  then changes retention to Interest. The resulting effective policy is
  Interest, so messages are retained only while a matching durable still has
  interest. The broad Activity filter matches every generic event, including
  events its handler ignores. Explicit Geodata commands are also stored in this
  stream under myota.geodata.> and each has one competing durable.
- **Interest is unsafe as the general domain-event policy.** A fact that has
  been acknowledged by every currently matching consumer disappears; a future
  consumer cannot replay that fact from the stream. A subject without a durable
  match can be discarded. Consumer creation before first publish mitigates
  only the latter and requires coordinated provisioning during rollout.
- **WorkQueue is unsuitable for shared domain facts.** It removes a message
  after its work consumer acknowledges it, which is correct for one competing
  worker group, but does not provide independent fan-out to multiple domain
  consumer groups. Interest and WorkQueue therefore describe different
  processing classes; they should not be selected by subject naming alone.
- **Replay is bounded and incomplete today.** The 30-day max age is a backlog
  safety limit, not an archive. Interest can remove an acknowledged event much
  earlier. Replaying a retained event requires a new consumer with a deliberate
  start policy; there is no documented operator replay/redrive procedure. Once
  expired or interest-deleted, JetStream cannot replay it. Relay and consumer
  dead-letter rows are database evidence, but no general redrive tool or
  idempotency-safe replay policy was found. Geodata can recover selected work
  from service-owned rows and migration 015; Activity jobs remain in
  activity_job. Outbox cleanup/retention across all owners needs confirmation.
- **JetStream deduplication is a short-window optimization.** The relay sets
  Nats-Msg-Id to eventId, but the documented default duplicate window is two
  minutes. Relay retry delays and operator replay can exceed that window.
  Stable IDs remain useful, but database-side idempotency is the correctness
  boundary; do not claim exactly-once side effects.
- **Three relays are database-specific, not three different routing policies.**
  Compose defines outbox-core, outbox-activity, and outbox-geo in
  **myota-deploy/compose.yaml**. Helm defines the corresponding Deployments in
  **myota-deploy/deploy/helm/myota/templates/deployment.yaml**. Identity,
  Programme, and Operations share core database relay access; this does not
  make their domain state one ownership boundary.
- **Operations is a read-only inspection boundary.**
  **myota-operations-service/operations.py** and
  **myota-operations-service/jetstream_observability.py** sample stream and
  consumer metadata and persist bounded snapshots. No Operations event call
  site or business consumer was found. It must not ack, purge, create/delete
  consumers, or become a work processor.

## Event-by-event inventory

For rows marked D, the exact current subject is mechanically generated as
myota.events. plus the event type with every period replaced by an underscore.
Current durable/filter and common delivery behavior are in profiles I/P/A/G,
R and N above. D means a domain fact; W means an event currently routed as work
because its payload carries an explicit subject. A work-routed row is not
available to generic domain subscribers on its current subject. “No consumer
found” is a current evidence statement, not a decision that no future consumer
is needed.

The selected fact target subject is myota.events.<eventType>, preserving the
event type's dot-separated tokens and final version token. For example,
identity.account.created.v1 becomes
myota.events.identity.account.created.v1. This replaces the current
dot-to-underscore transformation and enables family filters such as
myota.events.identity.>. Work subjects use the separate myota.work.<owner>.
hierarchy listed below. Subject changes require the compatibility rollout
recorded in the decision section; no runtime change is included here.

## Selected topology decision

**Decision:** keep one shared bounded domain-fact stream and create a separate
WorkQueue stream for each service owner with accepted competing work. Record
the event/envelope contract in myota-contracts during Phase 1. Provision and
validate JetStream resources through one deployment-owned reconciler in
myota-deploy, not from each of the three database relay replicas.

| Stream | Subjects | Retention and limits | Decision and tradeoff |
|---|---|---|---|
| MYOTA_EVENTS | myota.events.> | Limits; file storage; max age 30 days; finite MaxBytes, MaxMsgs, MaxMsgSize; DiscardNew | Holds committed facts for independent durable groups and a short replay window, including after ack. The database remains authoritative. Capacity pressure rejects new publishes so the relay can retry and alert instead of silently evicting an older fact. |
| MYOTA_ACTIVITY_WORK | myota.work.activity.> | WorkQueue; file storage; finite age, byte, message, and payload limits; DiscardNew | Isolates Activity import/render/database work from Geodata import and provider workloads. Six job kinds use disjoint filters and one durable per competing work kind; replicas share that durable. |
| MYOTA_GEODATA_WORK | myota.work.geodata.> | WorkQueue; file storage; finite age, byte, message, and payload limits; DiscardNew | Isolates PostGIS/import load and Geodata retry/recovery. Four job kinds use disjoint filters and one durable per competing work kind; replicas share that durable. |

Limits is selected for facts because messages remain available to independent
consumer groups after another group acknowledges them and can be replayed within
the bounded retention window. Interest would delete facts after all currently
matching consumers ack and can immediately discard a message with no matching
consumer. WorkQueue removes a message on its first consumer ack, which matches
one competing work group but breaks independent fact fan-out. These semantics
are described by the [NATS retention guidance](https://docs.nats.io/learn/jetstream/retention-policies).

The two work streams are a deliberate isolation boundary: Activity and
Geodata have different owning databases, worker pools, long-running operations,
retry rates, and recovery procedures. A single MYOTA_WORK stream would reduce
provisioning, but would couple their storage cap and backlog pressure. Separate
streams reduce that cross-service blast radius at the cost of two stream
configurations and dashboards. NATS allows multiple WorkQueue consumers only
when their subject filters do not overlap. Each stream therefore has one
non-overlapping filter/durable per work kind; workers of that kind share the
durable. See the [NATS retention guidance](https://docs.nats.io/learn/jetstream/retention-policies).

The selected work subjects use myota.work.* because today's MYOTA_EVENTS
captures both myota.events.> and myota.geodata.>. A subject may be stored by
only one stream. The new work prefixes do not overlap the existing stream's
capture, avoiding a stream-creation conflict during migration. Facts use
myota.events.<eventType> with dotted event type tokens, such as
myota.events.identity.account.created.v1. This makes family filters possible
and avoids the current dot-to-underscore encoding. NATS subject ownership and
overlap rules are described in [Your first stream](https://docs.nats.io/learn/jetstream/your-first-stream).

### Subject and consumer decisions

- Facts keep eventType as the versioned contract name and publish it as the
  suffix of myota.events.<eventType>. Register every type, owner, schema,
  payload bound, and subscriber disposition in myota-contracts. Use checked-in
  JSON Schemas there; a separate schema-registry service is not justified by
  this inventory.
- Activity notifications use scoped subscriptions: one filter for
  myota.events.identity.>, one for the exact Geodata review fact, and one for
  the exact Geodata status-change fact. Retire the current catch-all no-op
  filter. Start this side-effecting consumer at new messages; a replay must use
  an explicitly approved separate consumer so historical security notices are
  not resent by default.
- Activity migrates QSO_INGESTION, ADIF_IMPORT, AWARD_RECALCULATE,
  AWARD_EVALUATION, PDF_RENDER, and STATISTICS_REBUILD. NOTIFICATION_SEND is
  excluded because its current handler only changes a database status and does
  not deliver externally; remove that synthetic job or make its state
  transition accurate. If external delivery is added later, create a
  provider-backed command with a separate idempotency contract.
- Geodata migrates preprocessing, promotion, confirmed deletion, and location
  enrichment. Startup recovery and DB lease reconcilers remain recovery paths;
  retention cleanup remains scheduled maintenance. The service DB remains the
  source of truth and must recreate lost unacked work before queue expiry.
- Use one durable per competing work kind, with distinct filters within each
  WorkQueue stream. Scale replicas by binding to the same durable. Bound
  MaxAckPending to measured worker concurrency; keep it at one where a Geodata
  job must serialize and raise it only with load and correctness evidence.
- Every consumer has explicit ack policy, ack wait, bounded delivery count,
  backoff, and a documented unknown-version path. Ack only after the effect and
  idempotency/checkpoint commit. Keep stable eventId as Nats-Msg-Id and use a
  stable workId from the owning job/resource as the database idempotency key.
  NATS duplicate suppression is limited to its configured window; it is not an
  exactly-once guarantee. See [NATS publishing and deduplication](https://docs.nats.io/learn/jetstream/publishing).
- Keep envelopeVersion separate from the event payload's .vN suffix. Add
  envelopeVersion: 1, propagate a trusted request correlationId and optional
  causationId, and remove relay attempt count from the immutable published
  envelope. Keep retry attempts in outbox/DLQ state and telemetry.
- JetStream does not create a dead-letter queue automatically. On terminal
  delivery, persist an idempotent application dead-letter row before term,
  alert from both that row and the consumer max-deliveries advisory, and offer
  an authorized redrive tool that preserves workId and audit history. A message
  at MaxDeliver otherwise stops delivery without being copied to a DLQ. See
  [NATS acknowledgment and redelivery guidance](https://docs.nats.io/learn/jetstream/acknowledgment).
- For event replay, create a new isolated durable with an explicit start
  sequence/time; never rewind a production side-effecting consumer as a
  shortcut. For work, re-enqueue from the service DB with the same workId and
  idempotency guard. After the fact stream's retention window, rebuild current
  projections from source-of-truth state. If full historical facts are needed,
  add a service-owned history store; do not turn JetStream into an archive.
- Set finite message, byte, count, and age limits. Set DiscardNew on these
  critical streams so a full stream rejects new publishes and activates relay
  backpressure; DiscardOld could silently remove the oldest retained facts.
  Choose byte/count caps from measured peak traffic and allocated storage, and
  choose WorkQueue age from accepted recovery SLA plus maximum legitimate job
  duration. The NATS [stream shaping guidance](https://docs.nats.io/learn/jetstream/shaping-the-stream)
  explains these capacity and discard tradeoffs.

### Deployment and migration decisions

The current Compose NATS and Helm NATS are single-server deployments; Helm uses
one NATS replica and an 8 GiB PVC. Treat these as persistent single-node state,
not high availability. Keep replica count at one on the current topology.
Off-node backup is deferred at the workspace owner's direction; qualify restore
to a disposable PVC in the local K3s cluster. Loss of the node/cluster may lose
the bounded JetStream transport window, while PostgreSQL remains the source of
truth and supports work reconciliation/redrive. The production HA target is three
JetStream replicas only after a three-server NATS cluster is deployed; do not
configure three replicas against the current single-server service. NATS
documents that replication protects node loss but costs storage/write load and
does not increase write throughput in [Surviving node loss](https://docs.nats.io/learn/jetstream/surviving-node-loss).

Migration sequence:

1. Inspect the live stream and consumers; snapshot current state and confirm
   database outbox/DLQ recovery coverage. Stop relays before changing stream
   settings.
2. Deploy provisioning code that validates config but does not mutate streams
   from relay replicas. Change MYOTA_EVENTS from Interest to Limits through the
   single provisioner. NATS allows this live policy transition, but it cannot
   restore messages already removed under Interest; review the live config and
   counts first.
3. Create MYOTA_ACTIVITY_WORK and MYOTA_GEODATA_WORK with the disjoint
   myota.work.* subjects. Provision every durable before changing producers.
   WorkQueue is not a live retention conversion; use new streams.
4. Route pending legacy Geodata outbox rows to the new work subject in one
   publish path; do not dual-publish. Switch each accepted work producer only
   after its durable is ready, and keep DB state as the recovery source.
5. Observe outbox lag, queue age/depth, retry/DLQ counts, duplicate suppression,
   and database reconciliation. Drain old messages and durables; then disable
   old route mapping and remove the old work-subject capture only after rollback
   and recovery checks pass.

NATS applies a Limits/Interest switch immediately; in particular, switching to
Interest removes already-acked/unmatched messages. WorkQueue cannot be selected
as a live retention change. These are documented in [NATS retention guidance](https://docs.nats.io/learn/jetstream/retention-policies).
